Automation · resilience engineering

A bot that never stops

The interesting part of an autonomous publishing agent was not the writing. It was surviving quota walls, dead models and a server with no disk.

RoleArchitecture, build, operations
RuntimeRender, ephemeral disk
FocusResilience, not copywriting

What it is

An agent that plans, writes and publishes LinkedIn posts on a schedule, learning from what has worked before. The writing is the visible part. The engineering is everything that keeps it running when the provider misbehaves, which, on a free tier, is most days.

Failure one: quota walls

The first version crashed whenever Gemini's free tier hit a quota limit while processing a complex prompt. The fix was a key rotation engine: a pool of API keys in the environment, with the server intercepting 429 (quota exceeded) and 400 (invalid key) responses and rotating to the next credential instead of taking the process down. What used to be an outage became a retry.

Failure two: models going dark

Models also go offline or return 503 under load. A single fixed retry list handles that badly, because the right fallback depends on why the call failed. So the agent uses a dual-axis fallback matrix: it cascades from the most capable model down to a more stable one, choosing the path by error class. The result is that a degraded provider costs latency, not uptime.

Failure three: the server forgets everything

This is the one most people miss. Eyeno, the prompt architect behind the agent, was learning genuinely useful structures and then losing them, because Render's disk is ephemeral. Every deploy erased the brain.

The fix was to stop treating the container as storage. The server talks to the GitHub REST API and commits each new Markdown memory node straight to the repository. The vault becomes the source of truth; the runtime becomes disposable.

If state is worth keeping, keep it somewhere designed to keep it, and let the server be replaceable.

Why this is the interesting part

Anyone can wire a model to a posting endpoint. Making that survive real conditions, quotas, provider incidents, redeploys, cold starts, is the difference between a demo and something you can leave running overnight. The same three patterns (rotate, cascade by error class, externalise state) now run behind ForChi and REZMO too.
