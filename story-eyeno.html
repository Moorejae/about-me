Eyeno: the prompt architect that trains itself

A workspace that diagnoses a prompt before it runs, backed by a knowledge vault you can read, version and correct, then commits what it learns back to GitHub.

The flaw in most prompt workflows

Most AI systems have no memory of how you think. You start a chat, train it with your guidelines, and the moment that session closes the context is gone. Eyeno is an attempt to build a permanent, compounding layer instead of a better single prompt.

Part one: the Prompt Architect

The workspace takes a raw, ambiguous request, "make me a react component", and runs it through a diagnostic pipeline. It rates the draft across prompt-engineering dimensions:

  • Role and persona: who the model is acting as, and whether the draft says it.
  • Objectives and delimiters: what success looks like, and where the input stops being input.
  • Variables: what must be filled in before the prompt is allowed to run.
  • Alignment: four questions asked back to the user before synthesis, not after.

Only then does it write the final system prompt, formatted in the structure the task actually needs rather than one house style.

Part two: the vault

Instead of relying on model defaults, the Architect queries Eyeno, a live semantic database held as an Obsidian Markdown vault on GitHub. It is seeded with specific mental models and boundaries, each a node with double-bracket links, so the behaviour is inspectable rather than buried in a weights file. If a rule is wrong, I can read it, diff it and fix it.

In parallel with any prompt query, the backend runs a semantic check against the vault. If the prompt touches a known boundary, the relevant principles are pulled and merged into the output before the user ever sees it.

Part three: the loop that makes it compound

When a prompt is finalised and returned, the backend launches an asynchronous distillation job. A model reads the finished prompt, extracts the reusable pattern, formatting technique, domain context, structural choice, writes it as a clean Markdown node with wikilinks, and commits it to the vault repository.

The brain does not live in the container. It lives in a repository that outlives the container.

Keeping it alive when the provider is not

The first version crashed whenever Gemini's free tier hit a quota wall. Three fixes turned that into a system:

  • Key rotation. A pool of API keys in the environment; a 429 or invalid-key response rotates to the next credential and retries instead of taking the process down.
  • Dual-axis fallback. When a model goes offline or returns 503, the request cascades from the most capable model to a more stable one, chosen by error class rather than a single fixed retry list.
  • Memory that survives redeploys. Render's disk is ephemeral, so a file-based brain resets on every deploy. Committing to GitHub over the REST API makes the vault the source of truth and the runtime disposable.

Pipeline overview: the prompt checks and the vault nodes they query.

What it taught me

Prompt quality is a systems problem. The useful move was not writing better prompts, it was building the loop that captures what made a prompt good and keeps it. That is the same instinct behind the memory layer in REZMO, applied to a single person's working style instead of a user's whole history.
