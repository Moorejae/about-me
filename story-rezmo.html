REZMO — memory that belongs to the user

Every assistant keeps a summary of your work and forgets the files. REZMO keeps the whole record in a Drive you own, then serves it to whichever model you point at it.

RoleProduct, backend, infra, SEO
Live atrezmo.online
StackNode, Postgres 17, Redis, Cloudflare

The problem worth solving

Every AI product keeps a memory of your work, and every one of those memories is a summary written by the assistant, held by the assistant, and readable only inside that product. Switch tools and the record resets to a thinner copy of itself. After enough switches the work is gone and only summaries of it survive.

REZMO takes the opposite position: the record is the asset, and the models are readers of it.

Ownership as an architecture decision

A user's conversations, notes, projects and generated documents are stored as their material, with a copy in a folder in their own Google Drive. If REZMO disappeared tomorrow, that folder would still open. That single constraint decided almost everything else in the build.

  • Full depth, not digests. The record keeps files, not a paragraph about the files, so a later model can return to the source.
  • Portable by default. Download the folder, keep it offline, push it back, continue as if nothing was lost.
  • Many models, one record. One history that travels with the user instead of being rebuilt in every new chat.

Why MCP, not another chat window

The answer to "which tool remembers your work?" is not a better chat window. It is a record that lives outside all of them. REZMO runs a Model Context Protocol server, so Claude, ChatGPT, Grok, Cursor or any other MCP-capable client can be pointed at the same record.

The permission model matters as much as the protocol. The user approves each connection in the browser and decides whether a client may only read, or may also add to the record. Memory is not something a model should be able to write to silently.

Design ruleGive the model a role, not the keys. Read-only versus read-write is the simplest permission model that still respects the user.

Topology: one host, an edge worker, and a very short trip to the database

The API, Postgres 17 and Redis run as containers on a single Contabo host behind Cloudflare. The frontend is a Cloudflare Worker. Keeping the pieces few was a deliberate trade: one host is easy to reason about, easy to back up, and cheap to run.

Cloudflare does more than sit in front: DNS, WAF rules and TLS terminate at the edge, and the Worker is the only public entry point to the API. The origin only answers traffic that arrives through Cloudflare.

The performance lesson was about placement, not hardware. For a request path that touches the database several times per call, a 22× shorter round trip is the difference between a product that feels instant and one that feels broken. The trade is that the host becomes a real dependency — which is exactly why the record also lives in the user's Drive.

Tests are why I can move fast on it

That coverage sounds excessive until you consider what the product does: it reads and writes a user's own history. A regression here is not a visual bug, it is lost context. The suites cover Postgres and Redis behaviour, the permission boundary between read-only and read-write clients, the Drive synchronisation path, and the approval flow on the frontend — because the moment a user cannot tell what a model is allowed to do, trust is gone.

Payments run live through Paystack, which adds the usual requirement that nothing in the entitlement path is allowed to be flaky.

SEO: making a new product findable

A product with no search presence does not exist. The SEO work on REZMO was not a plugin install — it was structuring the site so both search engines and AI crawlers can understand and quote it.

  • One page per intent. Separate pages for the product overview, AI memory, and the MCP integration, so a search for "AI memory layer" and a search for "MCP server" both land somewhere specific instead of a generic homepage.
  • Semantic structure and metadata. Real headings in order, descriptive titles and metas per page, canonical URLs, and Open Graph tags so links unfurl correctly when shared.
  • An llms.txt file so language models crawling the site get a clean, factual summary of what REZMO is and what it does — instead of inferring it from marketing copy.
  • Trust pages. Terms, privacy, refund and cookie policies built out as real pages. For a product that stores personal history, those pages are part of the conversion surface, not legal decoration.
  • Performance as a ranking input. Static delivery at the edge, compressed assets and no render-blocking bloat — the same latency work that made the app feel fast also made it cheap to crawl.
The best SEO decision I made was having a real product with a real purpose, then writing down honestly what it does.

Email is part of the stack too

REZMO's mail is self-hosted on its own domain: mailboxes served from my own host over IMAP and SMTP instead of handed to a third-party provider. Account mail, the domain's DNS and the product sit under one operator, and the domain's SPF, DKIM and DMARC records are mine to get right. Same trade as the rest of the system — fewer moving providers, more responsibility.

What I took from building it

  1. Ownership is an architecture decision. Putting the record in the user's Drive changed the schema, the sync path and the failure modes — and it is the reason the product is credible.
  2. Latency is a placement problem first. Before optimising queries, check what the query is crossing.
  3. Test the product's promise. The promise is "your history is still here". Test that, not the button colours.
