ForChi: one agent, three jobs

A Telegram bot that publishes to two social networks, produces and uploads videos, and hunts for jobs, in parallel, unattended, on free infrastructure.

RoleDesign, build, operations
StatusRunning in production
Cadence5 posts/day · 2 videos/day · job scan every 30 min

What it does

Most "AI agent" demos are a single task wrapped in a chat window. ForChi is the opposite: one bot that runs three independent production workflows in parallel.

  • Social: writes the copy with Vertex AI, generates the image on a Hugging Face model, and publishes to Facebook and LinkedIn five times a day.
  • Video: scripts, voices and assembles YouTube uploads, up to two a day.
  • Jobs: scans boards every 30 minutes, scores each role against my profile with Gemini, and applies through Lever and Ashby.

Together those three loops used to eat most of a working day. Running them as one agent cut the manual time by roughly 99.9%.

The hard part: deciding when not to act

The failure mode of an always-on agent is not that it is dumb, it is that it is eager. If a casual "hey, how's the job hunt going?" can trigger an application run, the agent is dangerous, and you will spend more time supervising it than doing the work yourself.

So ForChi has a deterministic trigger layer in front of the model:

  1. Regex gate. The message must match an explicit command shape. Ordinary conversation never gets past this point, however it is phrased.
  2. Schema extraction. Once past the gate, a Zod schema validates the extracted parameters, target role, location, posting age, board, before anything executes. A missing or malformed field fails closed.
Deterministic code owns the whether. The model owns the what.

The social workflow: image and copy, end to end

The social lane is not just "post some text". Each post is a small production job:

  1. Copy: written by Gemini through the Google Vertex AI API key, so generation runs inside a Google Cloud project with its own quotas and audit trail rather than a personal key.
  2. Image: generated on a Hugging Face image model (my own Space), so the visual matches the post instead of shipping a stock photo.
  3. Publish: the pair is pushed to Facebook and LinkedIn five times a day, with the platform-specific formatting handled per target.
  4. Learn: the outcome is logged, so the next post starts from what actually performed.

That is the part people underestimate: a text model plus an image model plus two publishing APIs is four failure domains, and the workflow has to survive any one of them being down at 6am. It does, because the image and voice layers are Spaces I host, components I can restart, not vendors I have to wait for.

The model stack

Judgement calls, matching a posting to my actual experience, writing copy in my voice, picking a video angle, run on Gemini via Vertex AI. Its free tier is generous but not guaranteed, so the stack degrades instead of dying: a Qwen2.5-7B model I host on Hugging Face takes over as fallback.

Hugging Face carries more than the fallback model. ForChi uses an image Space for post visuals (and the YouTube thumbnails) and two voice Spaces (F5-TTS and Higgs TTS 3) for narration, so the whole content stack can be rebuilt from components I control.

Scheduling three workflows in one process

Each workflow has its own interval and its own failure blast radius. A forty-minute video render must not block the job scan that runs every thirty, and a failed social post must not take down the scheduler.

  • Every workflow writes its result, success or failure, so a silent stop is visible.
  • Retries are bounded and idempotent: an application is never submitted twice for the same role, even if the board returns the listing again.
  • Configuration lives in the environment, so a schedule change is a config change.
  • Long polling instead of webhooks. No public callback to keep registered, no tunnel to maintain, and the bot recovers on its own after a restart.
  • A real health endpoint. / returns a cheap status document and /status reports workflow state, so an external keep-alive is enough to know the process is alive and to wake it when it is not.

What I would tell anyone building this

  1. Guardrails before intelligence. Build the gate first. A precise agent that refuses ambiguous input beats a clever one that guesses.
  2. Log the decision: not just the action. When a workflow does not fire, the reason is the most valuable line in the log.
  3. Free tiers are a design constraint: not a hack. A system that survives cold starts and quotas ends up simpler and cheaper than one that assumes a warm server.
