CloudVoid — a wallet, and what it taught me

Fifteen chains, keys that never left the device, and a backend that only ever saw public addresses. Decommissioned as a product; kept as the reference build for everything that followed.

RoleArchitecture, backend, mobile, ops
StatusDecommissioned 2026
Still onlinecloudvoid.online

What it was

CloudVoid was a non-custodial multi-chain wallet covering 15 chains. "Non-custodial" is a claim most products make loosely, so the architecture had to make it true: private keys were generated on the device and never transmitted. The backend only ever received public addresses.

Keeping the backend blind

The hard part is that a backend usually still needs to correlate a user with their activity. The solution was an encrypted envelope rather than a shared secret:

  • P-256 ECDH for key agreement between the client and the service.
  • HKDF-SHA256 to derive separate encryption and authentication material.
  • AES-256-GCM for the payload, so tampering fails loudly instead of silently.
  • The master key on a separate host from the application and its data, so a breach of one box does not hand over both halves.
Principle that outlived the productSeparate the key from the data. Any system where one compromised host yields both has already lost.

Runtime hardening

Encryption protects data at rest and in transit. It does nothing if an attacker is already executing on the box. So the runtime was designed to assume that had happened:

  • Root SSH disabled, access restricted to specific keys from specific hosts.
  • UFW and iptables closing everything that was not explicitly needed.
  • Cloudflare in front, so the origin only answered edge traffic.
  • PM2 monitoring with an automated lockdown — on detected tampering or unusual egress, the app stops and the compromised user is isolated before data can leave.
  • Return-to-source — a reset that discards local changes and restores the verified state from GitHub, so malware does not survive a restart.

Why I retired it

CloudVoid was a real product with real users, and retiring it was a decision, not a failure. A non-custodial wallet carries an operational burden that never sleeps: any bug is a funds bug, and the security work is permanent rather than a launch checklist. I chose to stop operating that risk surface and carry the patterns into systems where the failure mode is a lost request rather than a lost balance.

The code and the domain are still up at cloudvoid.online as a reference build — the onboarding flow still runs.

The archived wallet at cloudvoid.online: the non-custodial onboarding flow.

Where the patterns went

The envelope encryption, the split key host, the hardened ports, the monitored runtime and the return-to-source routine now protect REZMO and the automation systems I run. That is the honest return on the project: not a wallet in the app stores, but a security posture I reuse every week.
